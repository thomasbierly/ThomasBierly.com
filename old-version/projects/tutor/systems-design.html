1. Executive Summary

RMIT University's Schools of Science, Engineering, and Computing employ hundreds of sessional (casual) tutors each semester to deliver tutorial and laboratory sessions. Historically, course coordinators managed tutor allocation manually — a process prone to scheduling conflicts, inequitable workload distribution, and significant administrative overhead.

The RMIT Tutor Scheduling Platform automates this entire workflow. Tutors submit their availability and course preferences online. Administrators review applicants and upload class schedules. Course coordinators run a mathematical optimization algorithm that produces a globally optimal, conflict-free allocation in under two minutes. Coordinators can pre-assign specific tutors to classes before running the optimizer, review results, make drag-and-drop adjustments, and send digital offers. Tutors accept or reject offers through a dedicated portal.

The platform is built as a TypeScript monorepo with a Next.js 15 frontend, Express.js backend, PostgreSQL database (via Prisma ORM), and a Python FastAPI microservice hosting the OR-Tools CP-SAT constraint programming solver. It is deployed on Railway and designed to be migrated to AWS as RMIT scales adoption.

Pilot Scope: The initial pilot targets approximately 500 sessional tutors, 150 course coordinators, and 325 classes across 4 semesters per year (Semester 1, Semester 2, Summer A, Summer B).

2. System Overview & Goals

2.1 Business Goals

  • Eliminate scheduling conflicts — No tutor can be double-booked across overlapping time slots in any course.
  • Fair workload distribution — The optimizer enforces fairness: every selected tutor reaches a baseline tutorial count before any tutor receives additional assignments.
  • Quality-weighted allocation — Tutors with higher CES (Course Experience Survey) scores and stronger admin preference ratings are preferentially allocated.
  • Manual override capability — Coordinators can pre-assign themselves or specific tutors to classes; the optimizer respects these decisions and only fills remaining slots.
  • Digital offer management — Tutors receive, accept, or reject offers digitally, eliminating email chains.
  • Audit trail — Every allocation decision, status change, and administrative action is logged.

2.2 Non-Goals (Pilot Scope)

  • RMIT Single Sign-On (SAML/SSO) — deferred to post-pilot; architecture supports it via Passport.js strategy pattern.
  • Real-time notifications (WebSocket) — email notifications only for now.
  • Mobile native apps — responsive web only.
  • Integration with RMIT's HR or payroll systems.

5. User Roles & Permissions

The platform uses Role-Based Access Control (RBAC). Every authenticated request passes through an Express middleware that checks the user's role before reaching the route handler. Roles are stored in the User.role field and embedded in the JWT payload. The six roles form a loose hierarchy of trust, with each higher role having broader organisational scope.

5.1 Role Hierarchy

COLLEGE_ADMINTheir collegeManages schools within their college, assigns school admins, views college-wide workload metrics.
UNI_ADMINUniversity-wideManages the college hierarchy and assigns college admins.
SUPER_ADMINSystem-wideOverride any allocation, change any user's role, impersonate users for support, view system diagnostics.

5.3 RBAC Middleware

The requireRole(...roles) middleware is applied per route group. It reads the role claim from the verified JWT and returns HTTP 403 if the role is not in the permitted list. It is applied after the authenticate middleware which verifies the JWT signature and expiry.

// Example route protection
router.get('/applicants', authenticate, requireRole('SCHOOL_ADMIN'), getApplicants);
router.post('/optimize', authenticate, requireRole('COORDINATOR'), triggerOptimization);
router.patch('/offers/:id', authenticate, requireRole('TUTOR'), respondToOffer);
router.get('/my-college', authenticate, requireRole('COLLEGE_ADMIN'), getCollegeOverview);
router.post('/impersonate', authenticate, requireRole('SUPER_ADMIN'), impersonateUser);

Time windows during which a tutor is available to teach. Stored as day-of-week + start/end time tuples. Multiple records per tutor. CourseInterest

Records a tutor's interest in teaching a particular course. Required for optimizer eligibility — tutors who have not expressed interest in a course are excluded from that course's optimization run entirely, regardless of availability.

ClassPreference

Records a tutor's preference for a specific class slot. Informational — no longer used for optimizer eligibility (switched to CourseInterest + availability). Coordinators can view which tutors prefer which classes on the schedule page.

CesScore

Course Experience Survey score for a tutor in a specific course and semester. Uploaded by admins via CSV. The most recent score per tutor-course pair is used by the optimizer as a quality signal. Unique constraint on [tutorProfileId, courseId, semester] prevents duplicates.

OptimizationRun

Records each invocation of the optimizer for auditing and debugging. Stores the solver parameters, final status, objective value, solver time, and a JSON summary of results including any unassigned classes and tutor workload distribution. Assessment

Defines assessments for a course (up to 3 per course). Each assessment has a title, weighting, optional word count, and flags for group work and in-class presentations. Used by coordinators to assign marking responsibilities.

MarkingAssignment

Editable transactional email templates stored in the database. Admins can modify subject and body via the UI. Templates use handlebars-style variable substitution (e.g. {{tutor_name}}). The variables field lists which substitution variables the template expects.

CoordinatorTutorRanking / CoordinatorCourseRanking

Coordinators can rank tutors for their courses at two levels of granularity. These rankings are factored into the optimizer's quality score, allowing coordinators to express preferences beyond what CES scores capture.

  • CoordinatorTutorRanking — class-level: coordinator ranks tutors for a specific ClassSlot (e.g. "I want Alice for T01 specifically").
  • CoordinatorCourseRanking — course-level: coordinator ranks tutors for the entire course (e.g. "Bob is my preferred tutor for COSC2531 generally").

Both tables store coordinatorId, the target entity ID, tutorId, and an integer rank. Class-level rankings take precedence over course-level rankings in the objective function.

9. Optimization Engine

The optimizer is a Python 3.13 FastAPI microservice hosting an OR-Tools CP-SAT constraint programming solver. It is called by the Express backend (via the BullMQ worker) with a JSON payload and returns a JSON assignment solution. It does not access the database directly — all data assembly happens in the TypeScript optimizer.service.ts.

9.1 Problem Formulation

The tutor allocation problem is formulated as a Constraint Satisfaction/Optimization Problem (CSOP). Given:

  • A set of tutors T, each with availability windows, a preference rating, and an optional CES score
  • A set of classes C, each with a day-of-week, start time, and end time
  • Configuration parameters: min/max tutorials per tutor, fairness threshold, CES weight

Find an assignment of tutors to classes that maximises a weighted quality objective while satisfying all hard constraints.

9.2 Decision Variables

# x[t, c] = 1 if tutor t is assigned to class c, else 0
# Created ONLY for (tutor, class) pairs where tutor's availability covers the class time
x = {}
for t in eligible_tutors:
    for c in classes:
        if tutor_available_for_class(t, c) and class_not_blocked(t, c):
            x[(t.id, c.id)] = model.NewBoolVar(f'x_{t.id}_{c.id}')

# y[t] = 1 if tutor t is selected (has at least one assignment)
y = {}
for t in eligible_tutors:
    y[t.id] = model.NewBoolVar(f'y_{t.id}')
Variable Reduction: By only creating variables for valid (tutor, class) pairs, the problem size is dramatically reduced. With 500 tutors and 325 classes, the naive matrix has 162,500 variables. After filtering by availability and course interest, this typically reduces to 5,000–20,000 active variables — a 90%+ reduction.

9.3 Constraints

C1 — Coverage (Hard)

Every class must be assigned exactly one tutor from the eligible pool. Classes with zero eligible tutors are detected before solving and reported as immediately infeasible.

for k in range(C):
    eligible_vars = [x[n][k] for n in range(T) if x[n][k] is not None]
    model.Add(sum(eligible_vars) == 1)

C2 — Load Cardinality (Hard)

Each tutor's load must be either zero (not selected) or within [min_tutorials, max_tutorials] (defaults: 2–6). This is enforced using an integer load variable ln and a boolean activation indicator an. The pattern ensures a tutor is never assigned exactly 1 class, which would be logistically impractical.

# load[n] = number of classes assigned to tutor n
ln = model.NewIntVar(0, max_t, f"load_{n}")
an = model.NewBoolVar(f"active_{n}")

model.Add(ln == sum(x[n][k] for k where eligible))
model.Add(ln >= min_t * an)    # if active, at least min_t
model.Add(ln <= max_t * an)    # if not active, must be 0

C3 — No Time Conflicts (Hard)

A tutor cannot be assigned to two classes that overlap in time. Overlap is pre-computed per tutor using interval arithmetic (same day, s1 < e2 AND s2 < e1). Back-to-back classes (e1 == s2) are not considered overlapping. Expressed as pairwise exclusion constraints on the binary decision variables.

for n in range(T):
    for (k1, k2) in conflict_pairs_by_tutor[n]:
        if x[n][k1] is not None and x[n][k2] is not None:
            model.Add(x[n][k1] + x[n][k2] <= 1)

C4 — Fairness Threshold (Soft, in objective)

Rather than a hard constraint, fairness is enforced via the objective function's lexicographic structure. An indicator variable over[n] is set to 1 if and only if tutor n's load exceeds the fairness_threshold (default: 3). The primary objective term -W × Σ over[n] uses a weight W large enough to dominate the quality term, ensuring the solver minimises the number of tutors exceeding the threshold before optimising assignment quality. Uses CP-SAT's only_enforce_if() for conditional indicator enforcement.

ov = model.NewBoolVar(f"over_{n}")
model.Add(ln > threshold).only_enforce_if(ov)
model.Add(ln <= threshold).only_enforce_if(ov.Not())

# W dominates quality: W = (max_quality × max_t + 1) × T
model.Maximize(-W * sum(over) + quality_sum)

C5 — Availability (Structural)

Enforced structurally: decision variables x[n][k] are only instantiated for (tutor, class) pairs where the tutor's availability windows cover the class time on the matching day of week. This is more efficient than explicit constraints and is the primary mechanism for reducing problem size.

C6 — Cross-Course Double-Booking Prevention (Structural)

Enforced in the TypeScript payload assembly layer (optimizer.service.ts), not in the Python solver. If a tutor has already ACCEPTED an allocation in another course that overlaps in time with a class in the current run, that class is added to their blocked_class_ids list. The Python solver receives eligible_class_ids per tutor and never creates variables for blocked pairs — making double-booking structurally impossible.

C7 — Weekly Teaching Hours Cap (Hard)

Enforces the RMIT workforce framework teaching hour limits. For sessional staff, the standard weekly cap is 36 contact hours (equivalent to the 38-hour standard week after applying the 3× teaching multiplier for a typical load), with an absolute maximum of 48 hours per week. The payload assembly layer calculates each tutor's projected weekly contact hours based on their existing ACCEPTED allocations and the classes under consideration in this run. Tutor-class pairs that would breach the weekly cap are excluded from the decision variable set before the solver runs — enforced structurally, not via explicit constraints.

# Pre-solver: exclude classes that would push tutor over weekly cap
for tutor in eligible_tutors:
    for week, classes_that_week in group_by_week(candidate_classes):
        existing_hours = accepted_hours_this_week(tutor, week)
        if existing_hours + class.duration_hours > weekly_cap:
            blocked_class_ids.add(class.id)

9.4 Objective Function

The objective is lexicographic — fairness is solved first, then quality is maximised within the fairness-optimal space. This is achieved by combining both goals into a single weighted sum where the fairness term dominates via a large coefficient W.

Quality Score Calculation

The quality score for a (tutor, class) pair combines the admin preference rating, CES score, and any coordinator rankings. Class-level coordinator rankings take precedence over course-level rankings when both exist.

def quality_score(tutor, class_slot, config) -> int:
    # Admin preference (global or per-course override)
    pref_weight = {"PREFERRED": 10.0, "OK": 5.0, "NOT_PREFERRED": 1.0}[tutor.preference]

    # CES score component
    ces_normalized = (tutor.ces_score or 0.0) / 5.0    # normalize [0,5] → [0,1]

    # Coordinator ranking component (class-level beats course-level)
    cc_rank_bonus = 0.0
    if tutor.class_rank is not None:        # class-level ranking exists
        cc_rank_bonus = max(0, 5.0 - tutor.class_rank)   # rank 1 → +4, rank 2 → +3, …
    elif tutor.course_rank is not None:     # fall back to course-level
        cc_rank_bonus = max(0, 3.0 - tutor.course_rank)  # rank 1 → +2, rank 2 → +1, …

    raw = pref_weight + config.ces_weight * ces_normalized + cc_rank_bonus
    return int(round(raw * 100))            # scale to integer (2 decimal precision)

Example: A PREFERRED tutor with CES 4.0, ces_weight 2.0, and class rank 1: 10.0 + 1.6 + 4.0 = 15.6 → 1560

Combined Objective

# Primary: minimise fairness violations (tutors exceeding threshold)
# Secondary: maximise total quality score

W = (max_quality_per_tutor * max_tutorials + 1) * num_tutors  # W dominates quality

model.Maximize(-W * sum(over[n] for n in tutors) + sum(quality[n] * x[n][k] for eligible pairs))

The weight W is computed to be strictly larger than the maximum possible quality sum. This guarantees the solver will always prefer an assignment with fewer fairness violations over one with higher total quality — even if the quality difference is enormous. Within solutions of equal fairness, the solver maximises quality.

9.5 Solver Pipeline

  1. Payload assembly (TypeScript, optimizer.service.ts): Queries DB for eligible tutors, classes, accepted allocations in other courses. Builds JSON payload.
  2. HTTP POST to optimizer: Sends payload to http://optimizer.railway.internal:8080/optimize. Timeout = time_limit + 30 seconds.
  3. Model construction (Python): Pydantic validates payload. OR-Tools model is built with variables and constraints as described above.
  4. CP-SAT solve: Solver runs with time_limit_seconds (default 120s) and num_search_workers = 8 for multi-core parallelism. Returns optimal or best-feasible solution found within the time limit.
  5. Response: Returns assignments array, objective value, solver time, unassigned classes, and tutor summary.
  6. Persistence (TypeScript): optimizer.service.ts bulk-creates Allocation records (status=PENDING), updates OptimizationRun with results.

9.6 Infeasibility Handling

Infeasibility is handled in two stages:

Pre-Solve Detection

Before the solver is invoked, the system checks whether any class has zero eligible tutors. If so, those classes are immediately flagged as infeasible and the response returns status: "infeasible" with the offending class IDs — no solver time is wasted.

Solver Failure

If the CP-SAT solver returns a status other than OPTIMAL or FEASIBLE, the response returns status: "infeasible" with all classes listed as unassigned. No constraint relaxation is attempted. The design choice is deliberate: silent relaxation could produce allocations that violate workload or fairness policies without the coordinator realising. Instead, the coordinator receives a clear failure signal and diagnostic data to inform manual intervention.

Diagnostics Payload

Every response — successful or failed — includes a diagnostics object containing:

  • bottleneck_classes — classes sorted by eligible tutor count (ascending), highlighting which classes are hardest to fill
  • day_concurrency — maximum number of overlapping classes per day of the week, indicating scheduling density
  • tutor_pool_size — number of eligible tutors in the run
  • variable_count — number of active decision variables after pre-filtering

Coordinators use this data to decide whether to exclude specific tutors, adjust availability windows, or manually pre-assign bottleneck classes before re-running the optimizer.

9.7 Manual Pre-Assignment Exclusion

Before building the optimizer payload, optimizer.service.ts queries for all Allocations where isManual = true for the target course. These class IDs are excluded from the optimizerClasses array passed to the Python service. The optimizer never sees or touches manually pre-assigned classes — they are transparent to it.

If all classes in a course are manually pre-assigned, the optimizer run is marked COMPLETED immediately with a "skipped" status and zero solver time.

9.8 Post-Optimization Marking Assignment Auto-Creation

Immediately after allocations are persisted from a successful optimization run, optimizer.service.ts automatically creates MarkingAssignment records following the teaching-tutor-marks-own-classes rule:

  1. For each course in the run, fetch all assessments and all new PENDING allocations.
  2. For each assessment × class combination, check if the teaching tutor has markingOptOut = false for this course.
  3. If no opt-out, create a MarkingAssignment (status = PENDING) linking the teaching tutor to the assessment for their class.
  4. If the teaching tutor has opted out, the slot is left unassigned for the coordinator to manually fill.
  5. If marking capacity would be exceeded (e.g. a tutor is already assigned too many submissions), a greedy overflow algorithm assigns the excess to the next eligible tutor in the pool — preferring tutors already teaching another class in the same course.
Default behaviour: The teaching-tutor-marks-own-classes rule is the default. Coordinators can override individual assignments via the marking page, and can opt tutors out on a per-course basis at any time. Auto-created assignments are overrideable — they are a starting point, not a lock.

13.2 Queue Configuration

16.2 Optimizer Performance

The CP-SAT solver is the primary performance concern. Benchmarks for the pilot scale (325 classes, ~500 tutors, ~20,000 active variables after filtering):

  • Typical solve time: 5–30 seconds for optimal solution
  • Hard cutoff: 120 seconds (returns best feasible solution found)
  • Variable reduction: Availability filtering reduces the variable matrix from 162,500 to ~5,000–20,000 — a 90%+ reduction that is the single most important performance optimization
  • Concurrent runs: Only one optimization job runs at a time per worker (CPU-bound). Multiple coordinators running simultaneously would queue.

16.3 Database Performance

All high-frequency query patterns are covered by indexes:

  • Tutor offers lookup: INDEX(tutorId, status) on Allocation
  • Optimizer availability queries: INDEX(tutorProfileId, dayOfWeek) on Availability
  • Class slot time queries: INDEX(dayOfWeek, startTime) on ClassSlot
  • Coordinator course filtering: UNIQUE(courseId, userId) on CourseCoordinator

16.4 Scaling Options

If RMIT expands the platform significantly (multiple faculties, 2,000+ tutors):

  • Frontend: Next.js SSR scales horizontally with Railway replicas or CDN caching of static content.
  • Backend: Express.js is stateless (JWT cookies) — scales horizontally. Rate limiter must be moved to Redis for multi-instance consistency.
  • Optimizer: Each course optimization is independent. Multiple optimizer instances can run in parallel (one per course). Switch rate limiter to Redis-backed.
  • Database: PostgreSQL read replicas for reporting queries (workload overview, audit log). Connection pooling via PgBouncer if connection count grows.
  • Solver upgrade: If CP-SAT reaches limits, HiGHS (open-source MIP solver) is faster for large LP relaxations. PuLP's solver-agnostic API makes switching trivial.

18.3 Platform Compliance Measures

PrincipleImplementation
Collection minimisation (APP 3)Only data necessary for the allocation process is collected. No unnecessary demographic data, no social media links, no references beyond what is needed for qualification verification.
Purpose limitation (APP 6)Data is used solely for tutor allocation, workload management, and marking assignment. No secondary marketing or profiling use.
Data quality (APP 10)Tutors can update their own profile, availability, and course interests at any time. Coordinators see real-time data. CSV uploads validate data format before persisting.
Security (APP 11 / IPP 4)See Section 10 for full security controls: encryption in transit (TLS), hashed credentials (bcrypt-12), role-based access control, row-level data isolation, audit logging, rate limiting.
Access and correction (APP 12–13)Tutors can view and edit their own profile data through the self-service portal. Admins can correct records via the admin panel.
Cross-border transfer (APP 8)The platform is hosted on Railway (US-based infrastructure). Under APP 8, RMIT must take reasonable steps to ensure the overseas recipient complies with the APPs. Railway's data processing terms and HTTPS-only transport provide a baseline. For production, a formal Privacy Impact Assessment should evaluate whether additional contractual safeguards are needed, or whether migration to Australian-hosted infrastructure (e.g. AWS Sydney region) is required.
Data retentionNo automated deletion or archival policy is currently implemented. Before production, a retention schedule must be established in consultation with RMIT Records Management — typically 7 years for employment records.
Breach notification (NDB scheme)Under the Notifiable Data Breaches scheme (Part IIIC of the Privacy Act), RMIT must notify affected individuals and the OAIC if a data breach involving personal information is likely to result in serious harm. Sentry monitoring (Section 18, outstanding) and the audit log support breach detection.

18.4 Recommendations Before Production

  1. Privacy Impact Assessment (PIA): Conduct a formal PIA per RMIT's privacy framework before onboarding real staff data. This document provides the technical input; the PIA evaluates institutional risk.
  2. Data retention policy: Define and implement automated archival/deletion schedules in consultation with RMIT Records Management and Legal.
  3. Work restrictions flag: Implement the tutor-level hour restriction field before onboarding international student tutors, to prevent visa condition violations.
  4. EBA alignment: Configure optimizer constraints and workload reporting to match the current RMIT Enterprise Agreement's casual workload provisions.
  5. Hosting jurisdiction review: Evaluate whether Railway's US-based hosting is acceptable under APP 8 or whether Australian-hosted infrastructure is required. AWS Sydney region is the natural migration target.
