1. Executive Summary

The Double Diamond AI Platform is a multi-agent web application that guides teams through the four phases of the Double Diamond design process—Discover, Define, Develop, Deliver—using phase-specialised AI agents. Each phase is served by a distinct AI persona with hard behavioural constraints enforced through system prompts. An orchestrator agent manages transitions between phases by compressing artefacts into structured handoff briefs, ensuring that context and insights carry forward without loss.

Core Value Proposition

The platform addresses three systemic failures in design thinking facilitation:

  1. Phase drift: Without structural guardrails, teams skip phases, conflate discovery with solutioning, and lose research artefacts. The platform enforces phase discipline through AI agent constraints that are architecturally impossible to bypass.
  2. Context loss: Insights from early phases are rarely passed forward in a structured way. The orchestrator automatically compresses and carries artefacts between agents.
  3. Facilitator overload: A real-time facilitator dashboard provides visibility across all concurrent teams with intervention tools, reducing the need for constant manual check-ins.

Why Two Backend Services?

The decision to split the backend into Node.js and Python services is driven by three factors:

  • SDK quality: Python has the most mature Anthropic SDK and is idiomatic for AI/ML workloads. The streaming API, structured output parsing, and prompt engineering patterns are more naturally expressed in Python.
  • I/O characteristics: Node.js excels at WebSocket-heavy, I/O-bound workloads (managing hundreds of concurrent Socket.io connections). Python excels at the CPU-bound, latency-sensitive AI API calls.
  • Independent scaling: AI calls are expensive and bursty; WebSocket connections are lightweight but persistent. Each service can be scaled independently based on its resource profile.
  • Decoupled change velocity: Prompt engineering changes (Python) are decoupled from API and collaboration changes (Node), enabling parallel development.

Inter-Service Communication

The three services communicate through two channels:

  • Redis Task Queue (ai:tasks): The App Server pushes AI task payloads (team context, messages, artefacts) to a Redis list. The AI Service's background worker pops tasks using BLPOP for efficient blocking reads.
  • Redis Pub/Sub: The AI Service publishes streaming tokens, structured output, and completion events to Redis channels (ai:stream:{teamId}, ai:structured:{teamId}, etc.). The App Server subscribes to these channels and relays them to the appropriate Socket.io room.

3. Multi-Agent AI Architecture

Design Rationale: Why Separate Agents?

A single AI model, regardless of system prompt complexity, drifts across a long conversation. Ask it to "discover" and it starts defining problems. Ask it to "define" and it generates solutions. This is a fundamental property of large language models—they optimise for helpfulness, and helpfulness in a general conversation means moving toward answers.

The Double Diamond methodology requires the opposite: deliberately resisting the urge to converge prematurely in early phases. Separate agents solve this by making phase discipline an architectural constraint rather than a prompt suggestion:

  • Each agent's system prompt is its identity. The Develop agent cannot reopen the problem definition because it has no concept of a problem definition phase.
  • Each agent can evolve independently (e.g., giving the Discover agent web search without affecting other phases).
  • The shift in AI personality between phases is a feature—teams experience distinct collaborators.

Agent Registry

AgentPhasePersonaModelCore Constraint
ExplorerDiscoverWarm design researcherClaude SonnetNEVER suggest solutions or define problems
AnalystDefineIncisive strategistClaude SonnetNEVER generate solution concepts

Agent Behavioural Constraints

Discover Agent — Explorer

  • Must: Ask about users, experiences, observations. Surface tensions and surprises. Redirect solution-thinking back to curiosity.
  • Must not: Suggest solutions, define the problem, make convergent statements.
  • Triggers: sticky_board, empathy_map, stakeholder_map, assumption_map, aeiou_board, trend_timeline, extreme_user_map
  • Special rule: Every turn mentioning what a user says/thinks/does/feels must include a complete empathy_map artefact with all 6 fields, building incrementally across turns.

Define Agent — Analyst

  • Must: Demand specificity and evidence for every claim. Push toward a sharp, testable problem statement.
  • Must not: Generate solution concepts, accept vague problem statements, proceed without evidence.
  • Triggers: affinity_cluster, five_whys, fishbone_diagram, jobs_to_be_done, pov_statement, hmw_builder, criteria_board, persona_builder, problem_statement
  • Special field: votingEnabled set to true when ready to vote on HMW questions.

Develop Agent — Catalyst

  • Must: Use "yes-and" framing. Introduce provocations and "what if" scenarios. Push for 5–10 concepts before convergence.
  • Must not: Evaluate or critique ideas prematurely, allow fixation on a single concept, reopen problem definition.
  • Triggers: brainstorm_board, reversed_brainstorm, analogies_board, impact_feasibility, 2x2_matrix, dot_vote, concept_cards, concept_storyboard

Deliver Agent — Builder

  • Must: Drive toward specificity. Ask "how will you test that?" repeatedly. Insist on success criteria and implementation plans.
  • Must not: Reopen problem definition, entertain new concepts without evidence, accept vague implementation plans.
  • Triggers: prototype_spec, service_blueprint, test_script, feedback_grid, mvp_sorter, success_metrics, iteration_log, pitch_canvas, implementation_roadmap, business_model_canvas

Orchestrator Agent

  • Runs only at phase boundaries, never directly with teams.
  • Reads the full conversation and artefact set from the completed phase.
  • Evaluates whether the phase is genuinely complete (not just checking token counts).
  • Produces a structured JSON handoff document for the next phase agent.

Structured Output Format

Every agent response ends with a JSON block wrapped in <structured_output> tags. The AI Service parses this block using regex extraction and publishes it separately from the conversational text:

<structured_output>
{
  "uiMode": "sticky_board",
  "artefactsToAdd": [
    { "type": "sticky_note", "text": "Users feel overwhelmed by onboarding", "cluster": null }
  ],
  "artefactsToUpdate": [],
  "handoffReady": false,
  "suggestedPrompt": null
}
</structured_output>

The frontend strips the <structured_output> block from displayed messages. The parsed JSON drives three behaviours:

  • uiMode triggers a canvas component switch in the WorkspaceCanvas panel.
  • artefactsToAdd / artefactsToUpdate are persisted to the database and broadcast to all team members.
  • handoffReady enables the "Request Handoff" button for team leads.

Orchestrator Handoff Protocol

When a team lead requests a handoff, the App Server queues an orchestrator task containing the full conversation and all phase artefacts. The orchestrator produces:

{
  "stageComplete": true,
  "summary": "3-5 sentence synthesis of what the team learned and produced",
  "keyArtefacts": ["Brief description of each significant artefact"],
  "gaps": ["Any notable gaps or unresolved tensions to carry forward"],
  "handoffBrief": "Full briefing for the next phase agent",
  "sessionSummary": "Short summary for session persistence"
}

The handoffBrief is stored in the phases table and injected into the next phase agent's system prompt as semi-static context, ensuring continuity without requiring the next agent to read the previous phase's raw conversation.

Artefact Extraction Pipeline

In addition to the agent's explicit artefactsToAdd output, a background extraction service runs after every agent response to identify artefacts mentioned in natural conversation that the agent did not explicitly structure. This pipeline:

  1. Uses Claude Haiku (fast, cheap) to parse the last 6 conversation turns against 23 phase-specific tool extractors.
  2. Each extractor defines a type, action, instruction, and expected format.
  3. Actions include: create (new items), upsert (replace single-object artefacts like problem_statement), merge_empathy (accumulate empathy map quadrants), upsert_assumptions (match and append challenges), upsert_persona (match by name), update_five_whys (merge fields).
  4. Extracted artefacts are deduplicated against existing artefacts using case-insensitive, whitespace-stripped comparison across identifying fields (text, title, name, description, etc.).
  5. Results are published to ai:extracted:{teamId} for the App Server to persist and broadcast.
Design decision: Running extraction on Haiku rather than Sonnet keeps costs low while maintaining extraction quality. The extraction prompt includes existing artefacts to prevent duplication, and a strict instruction to only extract concrete observations from the team, never the agent's own questions or suggestions.

Context Window Management

Long design sessions can easily exceed the model's context window. Three layered strategies prevent this:

Layer 1: Conversation Windowing

Only the last 12 message turns are sent to the Anthropic API. Older messages are not discarded from the database—they are accessible through session summaries.

Layer 2: Artefact Compression

Current phase artefacts are injected into the system prompt as compressed one-liners rather than full JSON objects. Each artefact shows its type and most identifying field, truncated to 80 characters. The list is capped at 30 items. Format: [type] identifying_field...

Layer 3: Session Summarisation

At session boundaries (team disconnect or 30-minute inactivity), the system generates a 3–5 sentence summary using Claude Haiku. Summaries are stored in the session_summaries table with message range markers. Up to 3 recent summaries are prepended to the next session's context.

Prompt Caching Layers

The system prompt is structured to optimise for Anthropic's prompt caching:

  • Static (cacheable): Base phase system prompt—identical across all calls for a given phase.
  • Semi-static: Project brief and handoff brief—change only at phase boundaries.
  • Dynamic (per-turn): Session summaries and compressed artefacts—change with every interaction.

Nudge Generation

When teams appear stuck (no messages for a configurable period), the frontend can request a nudge via POST /nudge. The AI Service uses Claude Haiku to generate a first-person example reply ("We could try..." / "I noticed that...") that sounds like a real team member, not an instruction directed at the agent. This lowers the barrier for teams to re-engage without breaking the conversational flow.

4. Data Architecture

Why PostgreSQL

PostgreSQL was chosen over document stores (MongoDB, DynamoDB) for three reasons:

  • ACID compliance: A team must never see a corrupted or partial artefact set. Transactional integrity is critical for project state consistency.
  • JSONB flexibility: Artefact content varies significantly by type (a sticky note has different fields from an empathy map). JSONB columns provide schema flexibility without sacrificing relational integrity for the project/team/phase structure.
  • Scaling path: AWS Aurora Serverless v2 (production target) is PostgreSQL-compatible and provides cost-efficient auto-scaling.

The PostgreSQL connection pool is configured with: max 30 connections, idle timeout 30 seconds, connection timeout 5 seconds. This accommodates concurrent API requests while preventing connection exhaustion during load spikes. Drizzle ORM provides type-safe query building on top of the node-postgres pool.

5. Authentication & Authorisation

Invite-Only Registration

The platform uses invite-only registration for the pilot. There is no open sign-up. An admin generates invite tokens that are pre-associated with a specific team and role. The registration flow:

  1. Admin creates an invite token via POST /teams/:teamId/invite or POST /admin/bulk-invite (up to 200 per batch).
  2. Token is generated using crypto.randomBytes(32) — cryptographically secure, 64-character hex string.
  3. Token is single-use, expires in 48 hours (configurable via INVITE_TOKEN_EXPIRY_HOURS), and optionally pre-assigned to a specific email address.
  4. An invite email is sent (if email provided) containing a registration link with the token.
  5. On registration, the server validates: token exists, is unused, is not expired, and (if pre-assigned) matches the registering email.
  6. User is created, added to the pre-assigned team with the pre-assigned role, and the token is marked used—all within a single transaction.

JWT Dual-Token System

Authentication uses a two-token strategy with rotation:

TokenExpiryStorageClaims
Access Token15 minutesIn-memory (JavaScript variable)sub, email, role, teamId
Refresh Token7 daysHttpOnly, Secure, SameSite=Lax cookiesub, tokenId (DB reference)

Token rotation: On every refresh, the old refresh token is marked as revoked in the database and a new refresh token is issued. This limits the damage window if a refresh token is compromised—the attacker's stolen token becomes invalid as soon as the legitimate user refreshes.

Signing: Both tokens use HS256 (HMAC-SHA256) with separate secrets (JWT_ACCESS_SECRET, JWT_REFRESH_SECRET). The duration parser supports s/m/h/d format strings.

Password Security

  • Hashing: bcrypt with minimum 12 rounds. This is deliberately slow (approximately 250ms per hash) to resist brute-force attacks.
  • Minimum length: 8 characters, enforced via Zod schema validation on all auth endpoints.
  • Password reset: Generates a 1-hour token. After successful reset, all existing refresh tokens for the user are revoked, forcing re-authentication on every device.

Email Verification

After registration, a verification token (24-hour expiry) is generated and sent via SMTP. The user must click the verification link before the account is considered fully activated. The verification endpoint marks users.emailVerified = true and deletes the token.

Role-Based Access Control

RolePermissions
adminFull access: create cohorts, teams, invite tokens; view all users; trigger phase transitions; send system messages
facilitatorRead-only across all teams in cohort; send system messages; trigger phase transitions; access facilitator dashboard
team_leadAll member permissions + request phase handoff
memberChat with agent, edit artefacts, vote within their team

Enforced through two middleware layers:

  • requireAuth — Extracts and verifies the Bearer token from the Authorization header, attaches req.user.
  • requireRole(...roles) — Checks user role matches one of the specified roles. Returns 403 Forbidden if insufficient.
  • requireTeamMember — Verifies the user is a member of the team specified in route params. Admins and facilitators bypass this check for cross-team access.

Future SSO Path

The authentication system is deliberately abstracted behind an EmailPasswordAuthProvider service class. This interface-based approach allows adding SSO providers (SAML 2.0, OAuth 2.0) without restructuring business logic. The JWT claims structure (sub, email, role, teamId) is compatible with standard SAML assertion mapping.

6. Real-Time Collaboration

Why Socket.io

Socket.io was chosen over raw WebSockets or Server-Sent Events for three reasons:

  • Room abstraction: Maps directly to team projects. socket.join(teamId) and io.to(teamId).emit() provide clean room-scoped broadcasting.
  • Reconnection handling: Automatic reconnection with exponential backoff and long-polling fallback for restrictive corporate firewalls.
  • Horizontal scaling: The Socket.io Redis adapter shares room state across multiple App Server instances, enabling stateless deployment.

Room Model

Each team has one Socket.io room identified by teamId. On connection, the client authenticates via JWT in the handshake auth payload. After verification, the client emits team:join to enter their team room.

Presence System

Online presence is tracked in Redis with automatic expiration:

  • Key: presence:{teamId}:{userId} with a 35-second TTL.
  • Clients send a presence:heartbeat event every 30 seconds to refresh the TTL.
  • If a heartbeat is missed (network failure, tab close), the key expires and the server broadcasts presence:leave.
  • On team:join, the server scans all presence:{teamId}:* keys and sends a presence:sync with the current online member list.
  • On disconnect, if all team members are offline, the session summariser is triggered.

AI Streaming Relay

The App Server sets up a Redis subscription relay (setupRedisRelay) that listens on pattern channels (ai:stream:*, ai:structured:*, ai:complete:*, ai:error:*). When a message arrives on ai:stream:T1, it extracts the team ID from the channel name and emits agent:tokenStream to Socket.io room T1.

Conflict Resolution: Last-Write-Wins

For the pilot, artefact edits use Last-Write-Wins (LWW) with an optimistic UI and server-side timestamp validation:

  • Client applies the edit immediately (optimistic update).
  • The PATCH request includes an expectedUpdatedAt timestamp.
  • If expectedUpdatedAt < server's updatedAt, the server returns 409 Conflict, and the client must re-fetch.
  • Otherwise, the content is shallow-merged and the update is broadcast to the team.
Future: CRDT-based conflict resolution using Yjs is planned for a later release. LWW is sufficient for teams of 2–6 where true simultaneous editing of the same artefact is rare.

Input Validation

All POST and PATCH endpoints use Zod schemas for request body validation. Validation rules include:

  • Email format validation on all auth endpoints
  • Password minimum 8 characters
  • Chat messages maximum 10,000 characters
  • Enum validation on roles, themes, phases, and artefact types
  • Avatar index bounded 0–80
  • Bulk invite maximum 200 per batch

Pagination

Chat message history uses cursor-based pagination with a before parameter (message UUID). This avoids the offset-skipping issues common with traditional offset pagination in append-heavy datasets.

Token Refresh Interceptor

The API client wrapper (/apps/web/src/lib/api.ts) intercepts 401 responses and automatically attempts a token refresh before retrying the original request. This provides seamless session continuity without requiring re-login during normal usage.

Session Restoration

On application mount, App.tsx calls refreshToken(). If a valid refresh cookie exists, the session is restored silently, and the user sees their team page without a login prompt. A checking flag prevents flash of the login page during restoration.

9. Background Services

AI Response Handler

The AI Response Handler (/apps/api/src/services/ai-response-handler.ts) is a Redis subscriber that runs within the App Server process. It subscribes to five channel patterns and handles persistence and broadcasting:

ChannelAction
ai:complete:{teamId}Persist assistant message to chat_messages; broadcast to team room
ai:structured:{teamId}Create/update artefacts from artefactsToAdd/artefactsToUpdate; broadcast ui:modeChange
ai:extracted:{teamId}Process extracted artefacts by action type (merge_empathy, upsert_assumptions, upsert_persona, update_five_whys, upsert, create); auto-extract sticky notes
ai:orchestrator:{teamId}Store handoff brief to phase record; broadcast orchestrator result with key artefacts and gaps
ai:summary:{teamId}Persist session summary with message range references

Deduplication Strategy

The handler performs fuzzy deduplication before creating new artefacts. It uses word-based Jaccard similarity across multiple fields (text, title, name, fullText, description, cause, metric, task, and empathy map quadrants). A 75% word overlap threshold prevents duplicate artefacts that differ only in phrasing.

Session Summariser

The Session Summariser (/apps/api/src/services/session-summariser.ts) manages two triggers:

  • Inactivity timer: On each message, resetInactivityTimer(teamId, phase) starts a 30-minute countdown. When it fires, a summarisation task is queued if there are 4+ new messages since the last summary.
  • Team disconnect: When all team members go offline (detected via presence system), onTeamDisconnect(teamId) triggers an immediate summary.

The summarisation task is processed by the AI worker using Claude Haiku on the last 20 conversation turns, producing a 3–5 sentence summary stored in session_summaries.

Email Service

The email service uses Nodemailer with SMTP (configured for Resend) and provides three transactional email types:

  • sendVerificationEmail — 24-hour verification link
  • sendPasswordResetEmail — 1-hour reset link

All email sends are fire-and-forget to avoid blocking the request/response cycle.

Additional Security Measures

  • Email Enumeration Prevention: The /auth/forgot-password endpoint always returns success, regardless of whether the email exists in the system. This prevents attackers from discovering valid email addresses.
  • Socket.io Authentication: WebSocket connections require a valid JWT in the handshake auth payload. Unauthenticated connections are rejected before room membership.
  • Conflict Detection: Artefact updates include an expectedUpdatedAt timestamp. Stale updates receive a 409 Conflict response, preventing silent data loss from concurrent edits.
  • Error Obfuscation: The global error handler returns a generic 500 error message to clients. Detailed error information is logged server-side via Pino but never exposed to the client.
  • Content Security Policy: Currently disabled for development flexibility but should be enabled in production with appropriate directives.
Known limitation: Helmet's Content Security Policy (CSP) and Cross-Origin Embedder Policy (COEP) are currently disabled to allow flexible font/image loading during development. These should be configured with appropriate directives before production deployment.

This section describes the architectural extensions required to transform the platform from a pilot-grade application into a market-ready enterprise SaaS product with multi-organisation licensing, financial management, and compliance infrastructure.

Usage Metering

  organisation_id UUID REFERENCES organisations(id),

-- Aggregate index for fast billing queries
CREATE INDEX idx_usage_org_period ON usage_records(organisation_id, billing_period_start, record_type);

Every AI API call logs input and output token counts. The AI worker publishes usage data to a usage:record Redis channel, and the App Server persists it asynchronously. Monthly aggregates are reported to Stripe for usage-based billing on Enterprise tier.

Enforcement

  • Team limit: Checked at team creation time against organisations.max_teams. Returns 402 Payment Required with upgrade prompt.
  • Member limit: Checked at invite generation against organisations.max_members_per_team.
  • Token budget: Checked before queuing AI tasks. If monthly usage exceeds ai_token_budget_monthly, AI requests return a graceful "usage limit reached" message suggesting the org admin upgrade their plan. Existing artefacts and chat history remain accessible.
  • Feature gating: SSO, custom domains, API access, and advanced analytics are gated by subscription tier using a requireTier(...tiers) middleware.

  4. Invite distribution: Org admin invites facilitators and team members via bulk invite or email.
  5. Ongoing management: Org admin monitors usage, manages billing, and runs cohorts independently.
