Part 1

Working with an agent

An AI agent doesn’t just answer questions. It works on your files: it reads your data and your code, writes and runs new code, looks at what came out, and tells you what it did. Used well, that gives you more time for the research itself and a better record of how every result was made.

In this part
  • How an agent differs from a chatbot
  • What to hand over, and what to keep for yourself
  • Whether it’s cheating, the real risks, and how to guard against them
  • How to disclose it honestly

A chatbot tells you; an agent does

Most people meet AI as a chatbot: you type a question into a website and it answers from what it learned in training. The answer often sounds sure of itself even when it’s wrong, and a chatbot will happily invent a reference that doesn’t exist. If it writes code for you, you copy it into SPSS or R, run it, paste the error back, and go round again.

An agent such as Claude Code works differently. You open it in a folder on your own computer, and it can work with everything in that folder. Ask for a regression and it writes the code, runs it on your data, reads the output, fixes its own mistakes, and reports back with the code saved where you can read it.

A chatbot
  • Answers from memory
  • Can’t see your files
  • You copy its code in and its errors out
  • Its claims are hard to check
An agent
  • Works from your data and code
  • Reads and writes files in your project
  • Runs the code itself and fixes the errors
  • Leaves code you can read and run again

That last row matters most. A chatbot’s answer is a claim you have to take on trust. An agent’s work is code, and code can be checked: run it again and you get the same number, read it and you can see every step. Tom Pepinsky, a political scientist at Cornell, puts the line simply: use agents for tasks that follow rules, such as cleaning data, running models and drawing figures, and “do not use agentic AI for tasks that generate answers, arguments, or interpretations.”

What to hand over, and what to keep

Hand over
  • Cleaning, merging and reshaping data
  • Translating your old SPSS or Stata syntax, and checking the results match
  • Writing, running and rerunning analysis code
  • Tables and figures, in your journal’s style
  • Checking that every number in the text matches the analysis
  • Formatting, references and the PDF
  • Fixing the computer when something breaks
Keep for yourself
  • The question, and why it matters
  • The design: what would count as evidence
  • Which analyses to run, decided before you see the results
  • What the results mean
  • Every claim in the paper
  • Reading the work you cite

The agent is still useful on the right-hand side, as long as it advises rather than decides. Ask it to explain an output, to argue against your interpretation, or to list what a sceptical reviewer would ask. Paul Goldsmith-Pinkham, an economist at Yale who teaches researchers to work this way, describes agents as “editors and thinking partners rather than judgment outsourcers.”

Is it cheating?

No more than statistical software was. Nobody thinks the honest way to fit a regression is by hand, or that a paper is less yours because a research assistant cleaned the data. What makes research trustworthy has never been who typed the code. It’s whether the work is sound, whether you understand it, and whether someone else can check it.

Done the way this course shows, work with an agent is easier to check than most research done by hand. The analysis is code that anyone can rerun, the paper is built straight from it, and every change is recorded. Compare that with numbers copied by hand from an output window into Word.

Many researchers already use AI and keep quiet about it. In a 2026 survey of 2,606 researchers by Oxford University Press, 44% worried that disclosing it would colour how their work was judged, and 74% found the rules unclear. Silence is the bigger risk. It leaves no record, and no way to show that the work was done carefully.

You’d be in good company being open about it. Scott Cunningham, the Baylor economist behind Causal Inference: The Mixtape, has written a long public series on how Claude Code changed his research. Goldsmith-Pinkham recorded a video course for Princeton’s Markus Academy, Chris Blattman at Chicago wrote a guide for complete beginners, and universities such as Konstanz now teach it as a course.

The real risks, and how to guard against them

The concerns are real. Science magazine has reported automated “AI scientist” tools that made up data and p-hacked their results. An agent working in your project doesn’t remove your responsibility; it changes what you check. Here is what can go wrong, and how the setup in this course protects you:

The riskWhat can happenHow you guard against it
Making things upA number or a reference that sounds right but isn’tEvery number comes from code, never from the agent’s memory. References come from your own Zotero library.
Telling you what you want to hearThe agent leans towards the result it thinks you’re hoping forDecide your analyses before you see results, and write them down. Ask it to argue the other side.
Quietly cutting cornersA dropped case, a changed setting, a test left outNothing changes without a record: the review tab shows every line the agent changed before you save it.
Losing your grip on the analysisResults you can’t explain to a reviewerAsk the agent to explain each step until you could explain it yourself. Notebooks keep the explanation, code and results together.
Your data leaving your computerFiles the agent reads are sent to Anthropic to be processedCheck your ethics approval and your institution’s rules first. Keep identifiable data out of the project, or work on an anonymised copy.

Goldsmith-Pinkham’s summary is the one to remember: “Verification is the new bottleneck.” The agent makes producing work cheap. Your job is checking it, and the setup is designed to make checking easy.

Disclosure is easy when the record keeps itself

Journals and publishers increasingly ask how AI was used, yet in the same survey only 36% of researchers kept any record of it. In this setup the record keeps itself. Every version of the project is saved with a short description, and you can ask the agent to say in each one what it did and how it was checked. When a journal asks, you can answer precisely. For example:

Data cleaning and analysis code was written with the help of Claude Code (Anthropic), working in the project’s repository. All code was reviewed by the authors, every result in the paper is produced by that code, and the full history of changes is available in the replication package. The research design, interpretation and text are the authors’ own.

Adapt it to what you actually did, and check your journal’s policy.

Try it today, on the computer you have

You don’t need Linux or anything else from this course to feel the difference. Claude Code runs on Mac and Windows too. Give it twenty minutes with a small analysis you’ve already finished:

1
Get Claude
You need a paid Claude subscription; Pro is enough to start. Install the Claude desktop app, sign in, and open the Code tab. It includes Claude Code, so there’s nothing else to install.
2
Make a copy of a small, finished analysis
Put a copy of the data and your syntax or do-file in a new folder. A copy means nothing can happen to the original. Pick something without identifiable data.
3
Open the folder in Claude Code and ask
Choose the folder when Claude asks for one, then try a few of these. It will ask before it changes anything.
Understand

Look through this folder and explain what this analysis does, step by step.

What would a sceptical reviewer question about it?

Redo

Rewrite my do-file in Python and show me that the results match.

Make Figure 1 again, colour-blind friendly, and save it as a PDF.

Then read what it did: the code it wrote is in the folder. If something in that twenty minutes changes how you think about your work, the rest of the course builds a whole way of working around it, starting with the project itself.
