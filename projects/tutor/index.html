RMIT Tutor Scheduling Platform

Automated sessional tutor allocation for higher education — built end-to-end as a solo engineering project.

Visit the platform →

The Problem

Every semester, RMIT University's course coordinators spend days manually matching hundreds of sessional tutors to class slots — cross-referencing availability spreadsheets, avoiding double-bookings, ensuring workload fairness, and chasing acceptances via email. It's a process that's error-prone, time-consuming, and doesn't scale.

I built a platform to automate it entirely.

What It Does

The platform manages the full lifecycle of sessional tutor allocation — from application through to confirmed teaching assignment.

  1. Tutors submit their availability, course interests, and CV through a self-service portal.
  2. Administrators review applicants, upload class schedules and historical performance data via CSV, and manage the semester calendar.
  3. Course coordinators run a mathematical optimisation algorithm that produces a globally conflict-free, quality-weighted allocation across all classes in under two minutes — then review results, make adjustments on a drag-and-drop calendar, and send digital offers.
  4. Tutors accept or reject offers through the portal, with email notifications at every step.

The Optimisation Engine

The core of the platform is a constraint programming solver built in Python using Google's OR-Tools CP-SAT engine — the same solver used in Google's own logistics and scheduling systems.

The allocation problem is formulated as a Constraint Satisfaction and Optimisation Problem (CSOP). The solver must assign tutors to classes while simultaneously satisfying hard constraints and maximising a quality objective.

Hard Constraints
  • Every class receives exactly one tutor
  • No tutor is double-booked across overlapping time slots, including across different courses running simultaneously
  • Every assigned tutor receives a minimum of 2 classes (prevents impractical single-class assignments)
  • No tutor exceeds a configurable maximum load (default: 6 classes)
  • Tutors are only considered for classes that fall within their nominated availability windows
Fairness Constraint
  • A pairwise linearised fairness constraint ensures workload is distributed equitably — no tutor receives their 4th class until every other selected tutor has received at least 3
Objective Function
Maximise: Σ x[t,c] × (preference_weight[t] + ces_weight × normalised_CES[t])

Where x[t,c] is a binary decision variable indicating whether tutor t is assigned to class c. Tutors rated PREFERRED by administrators are weighted at 10, OK at 5. CES (Course Experience Survey) scores — historical student satisfaction ratings — are normalised across the pool and contribute an additional weighted term. This drives the solver towards allocations that prioritise high-quality, well-reviewed tutors while still satisfying all hard constraints.

Problem Size & Performance
  • At pilot scale (500 tutors, 325 classes), the naive decision variable matrix has 162,500 binary variables
  • Aggressive pre-filtering instantiates variables only for valid (tutor, class) pairs — reducing the active count by over 90% to approximately 5,000–20,000 variables
  • This makes the problem tractable for CP-SAT in well under the 120-second time limit
  • If no feasible solution exists, the solver applies cascading constraint relaxation — first relaxing minimum workload, then fairness — and returns a diagnostic report of which classes remain unassigned and why

Technical Architecture

The platform is a production-grade TypeScript monorepo deployed on Railway, built with a clean separation of concerns across four services.

Frontend
Next.js 15 (App Router)
SSR, file-based routing, TypeScript-first
Backend API
Express.js + Prisma ORM
Clean REST separation, type-safe DB queries
Database
PostgreSQL 16
Relational integrity, ACID compliance
Optimiser
Python 3.13 + FastAPI + OR-Tools
CP-SAT solver, private network only
Job Queue
BullMQ + Redis
Async solver runs — 120s jobs can't be synchronous
Email
Resend
Transactional offer notifications and confirmations
Security

bcrypt password hashing (cost 12), JWT access tokens in httpOnly/SameSite=Strict cookies, role-based access control on every route, row-level data isolation (coordinators can only access their own courses), Zod validation on all request bodies, Helmet.js security headers, rate limiting on auth endpoints, and a full immutable audit log.

The optimiser microservice runs on Railway's private internal network and is not accessible from the public internet — only the backend API can call it.
